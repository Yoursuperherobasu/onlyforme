# Observability Implementation Steps

This document describes all the code changes made to implement user-isolated observability in LangBuilder using Langfuse OSS.

---

## Summary of Changes

The observability feature enables users to monitor their AI usage, costs, tokens, and latency metrics through an integrated dashboard. Each user can only see their own traces, ensuring data isolation.

---

## Files Created

### 1. Backend API Endpoints

**File:** `langbuilder/src/backend/base/langbuilder/api/v1/observability.py`

**Purpose:** Provides REST API endpoints for the observability dashboard to fetch user-specific metrics from Langfuse.

**Key Features:**
- All endpoints require JWT authentication
- Data is filtered by the current user's ID
- Supports pagination for large datasets (Langfuse max 100 per request)
- Includes debug endpoint for troubleshooting

**Endpoints Created:**

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/api/v1/observability/status` | GET | Check Langfuse connection status |
| `/api/v1/observability/debug` | GET | Debug info for troubleshooting |
| `/api/v1/observability/traces` | GET | Get user's traces (paginated) |
| `/api/v1/observability/traces/{id}` | GET | Get specific trace with observations |
| `/api/v1/observability/sessions` | GET | Get user's chat sessions |
| `/api/v1/observability/sessions/{id}` | GET | Get session details |
| `/api/v1/observability/metrics` | GET | Get aggregated usage metrics |
| `/api/v1/observability/agents` | GET | Get agents (flows) with metrics |
| `/api/v1/observability/agents/{id}` | GET | Get agent detail with sessions |
| `/api/v1/observability/projects` | GET | Get projects (folders) with metrics |
| `/api/v1/observability/projects/{id}` | GET | Get project detail with agents |

**Response Models:**
- `LangfuseStatusResponse` - Connection status
- `ObservationResponse` - Single LLM call/span
- `TraceListItem` / `TraceDetailResponse` - Trace data
- `SessionListItem` / `SessionDetailResponse` - Session data
- `MetricsResponse` - Aggregated metrics
- `AgentListItem` / `AgentDetailResponse` - Agent (flow) data
- `ProjectListItem` / `ProjectDetailResponse` - Project (folder) data

**Helper Functions:**
- `get_langfuse_client()` - Creates Langfuse client from env vars
- `fetch_traces_from_langfuse()` - Fetches traces with pagination
- `fetch_observations_for_trace()` - Gets observations for a trace
- `parse_observation()` - Parses Langfuse observation to response model
- `_is_vertex_trace()` - Filters out vertex-level traces
- `_match_trace_to_flow()` - Matches traces to database flows

## Data Flow

### When a User Runs a Flow:

```
1. User clicks "Run" on a flow
2. build_graph_from_db_no_cache() extracts folder_id as project_id
3. build_graph_from_data() creates LangGraphAdapter with project info
4. LangGraphAdapter.initialize_run() starts tracing with project metadata
5. LangFuseTracer.setup_langfuse() creates trace with:
   - tags: ["flow_id:xxx", "flow_name:Agent1", "project_id:yyy"]
   - metadata: { flow_id, flow_name, project_id, project_name }
6. Trace is sent to Langfuse with user_id for isolation
```

### When a User Views the Dashboard:

```
1. User opens Observability page
2. Frontend calls /api/v1/observability/metrics (or other endpoints)
3. Backend extracts user_id from JWT token
4. Backend fetches all user flows from DATABASE (source of truth)
5. Backend fetches traces from Langfuse with user_id filter
6. Backend uses _match_trace_to_flow() to match traces to database flows
7. Vertex-level traces are filtered out
8. Data is aggregated and returned
9. Frontend displays filtered, user-specific data
```

## Security

- **Authentication:** All endpoints require valid JWT token
- **Authorization:** Backend filters ALL data by `current_user.id`
- **Data Isolation:** Users cannot access other users' trace IDs
- **Credential Security:** Langfuse credentials stay in backend (never sent to frontend)

## Troubleshooting

### No Data Showing

1. Click "Debug" button in the dashboard
2. Check if your user ID matches any traces in Langfuse
3. Verify Langfuse environment variables are set
4. Run a flow to generate new traces

### Costs Showing as $0.00

Configure model pricing in Langfuse:
1. Go to Langfuse dashboard → Settings → Models
2. Add your model with pricing info
3. Note: Cost is calculated at trace creation time, not retroactively

### Agent/Project Tab Empty

- Agents tab requires traces to be matched to database flows
- Projects tab requires flows to be in folders
- Old traces without metadata are matched by name
- Vertex-level traces (vertex_build_*) are filtered out

### Tokens Showing as 0 / Input-Output Not Showing

This can happen if the trace context is not properly propagated to LLM calls:

1. **Check trace structure:** Use the Debug panel to see if traces exist
2. **Verify callback propagation:** The `build_vertex` method should NOT create separate traces - it should use the trace context from `initialize_run()`
3. **Check tracing service:** Ensure `_tracing_service` is being passed to components
4. **LLM callbacks:** Components must call `get_langchain_callbacks()` when invoking LLMs

**Technical fix applied (v1.1):** Removed separate trace context creation in `adapter.build_vertex()` so that:
- All observations are nested under the main flow trace
- Token/cost data aggregates correctly on the flow trace
- Input/output data is captured by Langfuse callbacks

## Changelog

### v1.1 (Token/Input-Output Fix)
- **Fixed:** Removed separate trace context creation in `adapter.build_vertex()`
  - Previously, each vertex build created its own trace (`vertex_build_*`), which broke token aggregation
  - Now vertex builds use the trace context set up by `initialize_run()`
  - This ensures LLM callbacks capture tokens and input/output data correctly
- **Result:** Token counts, costs, and input/output JSON now display properly in trace details
