# Model Microservice Architecture (LLM & Embeddings)

## Overview

The LLM and Embeddings functionality has been decoupled from the monolithic backend into a standalone FastAPI microservice called **model-service**. The backend no longer imports any LLM provider SDKs (OpenAI, Anthropic, Google, Groq). Instead, it delegates all LLM chat completions, embedding generation, model registry CRUD, and test-connection operations to the microservice via HTTP.

## How Backend Connects to Microservice

### Configuration

Two environment variables in the backend `.env` file control the connection:

```
MODEL_SERVICE_URL=http://localhost:8001
MODEL_SERVICE_API_KEY=agentcore-model-svc-key-001
```

These are read by the backend settings class and made available via `get_settings_service().settings`.

### Authentication Flow

1. Backend reads `MODEL_SERVICE_URL` and `MODEL_SERVICE_API_KEY` from settings
2. Every HTTP request to the microservice includes the header `x-api-key: <MODEL_SERVICE_API_KEY>`
3. The microservice validates this header in its `verify_api_key()` dependency
4. If the key doesn't match `MODEL_SERVICE_API_KEY` configured in the microservice's own `.env`, the request is rejected with 401

### Request Flow: UI Flow Execution (LLM)

1. User builds a flow in the UI with a "Large Language Model" component
2. User selects a provider (e.g., OpenAI) and a registry model (e.g., GPT-4o)
3. When the flow executes, the component's `build_model()` is called
4. `build_model()` returns a `MicroserviceChatModel` proxy object (not a real ChatOpenAI)
5. The flow engine calls `.ainvoke()` or `.astream()` on this proxy
6. The proxy sends an HTTP POST to `{MODEL_SERVICE_URL}/v1/chat/completions` with:
   - `provider`: "openai"
   - `model`: "gpt-4o"
   - `provider_config.registry_model_id`: UUID of the registry entry
   - `messages`: the conversation messages
7. The microservice receives this, looks up the registry entry by UUID, decrypts the API key, builds the real ChatOpenAI instance, invokes it, and returns the response
8. The proxy parses the OpenAI-compatible response and returns it as a LangChain `ChatResult`

### Request Flow: UI Flow Execution (Embeddings)

Same pattern as LLM, but:
- Component's `build_embeddings()` returns a `MicroserviceEmbeddings` proxy
- Proxy calls `{MODEL_SERVICE_URL}/v1/embeddings`
- Microservice builds the real embeddings model (OpenAIEmbeddings, etc.) and returns vectors

### Request Flow: Model Registry CRUD

1. User adds/edits/deletes a model on the Model Registry page
2. Frontend calls backend API (e.g., `POST /api/v1/models/registry/`)
3. Backend's `model_registry.py` router forwards the request to the microservice:
   - `POST {MODEL_SERVICE_URL}/v1/registry/models` (create)
   - `GET {MODEL_SERVICE_URL}/v1/registry/models` (list)
   - `PUT {MODEL_SERVICE_URL}/v1/registry/models/{id}` (update)
   - `DELETE {MODEL_SERVICE_URL}/v1/registry/models/{id}` (delete)
4. The microservice performs the DB operation and returns the result

### Request Flow: External Application (Direct)

External applications (Python scripts, Postman, etc.) can call the microservice directly:

```bash
curl -X POST http://localhost:8001/v1/chat/completions \
  -H "x-api-key: agentcore-model-svc-key-001" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "openai",
    "model": "gpt-4o",
    "messages": [{"role": "user", "content": "Hello"}],
    "provider_config": {"registry_model_id": "<uuid>"}
  }'
```

## Microservice API Endpoints

All endpoints except `/health` require the `x-api-key` header.

### Health

| Method | Path | Description |
|--------|------|-------------|
| GET | `/health` | Health check (no auth required) |

### Chat Completions

| Method | Path | Description |
|--------|------|-------------|
| POST | `/v1/chat/completions` | Chat completion (streaming and non-streaming). Supports `stream: true` for SSE streaming. |

### Embeddings

| Method | Path | Description |
|--------|------|-------------|
| POST | `/v1/embeddings` | Generate embeddings for a list of texts. Returns OpenAI-compatible response. |

### Model Listing

| Method | Path | Description |
|--------|------|-------------|
| GET | `/v1/models` | List all active models from the registry |
| POST | `/v1/models/list` | List available models from a live provider API (e.g., fetch all OpenAI models) |

### Model Registry CRUD

| Method | Path | Description |
|--------|------|-------------|
| GET | `/v1/registry/models` | List registry entries. Query params: `provider`, `environment`, `model_type`, `active_only` |
| POST | `/v1/registry/models` | Create a new registry entry |
| GET | `/v1/registry/models/{id}` | Get a single registry entry by UUID |
| PUT | `/v1/registry/models/{id}` | Update a registry entry |
| DELETE | `/v1/registry/models/{id}` | Delete a registry entry |

### Test Connection

| Method | Path | Description |
|--------|------|-------------|
| POST | `/v1/registry/test-connection` | Test an LLM connection (sends "Hello" and reports latency) |
| POST | `/v1/registry/test-embedding-connection` | Test an embedding connection (embeds "Hello" and reports dimensions) |

## Encryption Key Derivation

The microservice shares the same `model_registry` table with the backend. API keys stored in this table are encrypted using Fernet symmetric encryption. The encryption key is derived from `WEBUI_SECRET_KEY`:

```
WEBUI_SECRET_KEY  -->  SHA-256 hash  -->  base64url encode  -->  Fernet key
```

Both the backend and microservice must derive the same key from the same `WEBUI_SECRET_KEY` to encrypt/decrypt API keys consistently.

## Running the Microservice

```bash
cd src/services/model-service
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -e .
cp .env.example .env           # Configure DB URL, encryption key, API key
uvicorn app.main:app --host 0.0.0.0 --port 8001 --reload
```

Verify:

```bash
curl http://localhost:8001/health
# {"status": "healthy"}
```

## Database

The microservice connects to the **same PostgreSQL database (coredb)** as the main backend. It reads/writes the `model_registry` table. No additional database setup or migrations are needed.

The `model_registry` table stores:
- Provider (openai, azure, anthropic, google, groq, openai_compatible)
- Model name, display name
- Encrypted API key (Fernet)
- Base URL, provider config (JSON)
- Model type ("llm" or "embedding")
- Environment, capabilities, default parameters
- Active/inactive status
