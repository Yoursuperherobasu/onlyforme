# MCP Microservice Architecture (Model Context Protocol)

## Overview

The MCP (Model Context Protocol) functionality has been decoupled from the monolithic backend into a standalone FastAPI microservice called **mcp-service**. The backend no longer imports any MCP SDK classes (MCPStdioClient, MCPSseClient, MCPSessionManager) or runs MCP subprocesses/SSE connections directly. Instead, it delegates all MCP registry CRUD, session management, tool discovery, and tool invocation to the microservice via HTTP.

## How Backend Connects to Microservice

### Configuration

Two environment variables in the backend `.env` file control the connection:

```
MCP_SERVICE_URL=http://localhost:8002
MCP_SERVICE_API_KEY=agentcore-mcp-svc-key-001
```

These are read by the backend settings class and made available via `get_settings_service().settings`.

### Authentication Flow

1. Backend reads `MCP_SERVICE_URL` and `MCP_SERVICE_API_KEY` from settings
2. Every HTTP request to the microservice includes the header `x-api-key: <MCP_SERVICE_API_KEY>`
3. The microservice validates this header in its `verify_api_key()` dependency
4. If the key doesn't match `MCP_SERVICE_API_KEY` configured in the microservice's own `.env`, the request is rejected with 401

### Request Flow: UI MCP Registry CRUD

1. User adds/edits/deletes an MCP server on the MCP Registry page
2. Frontend calls backend API (e.g., `POST /api/v1/mcp/registry/`)
3. Backend's `mcp_registry.py` router forwards the request to the microservice:
   - `POST {MCP_SERVICE_URL}/v1/mcp/servers` (create)
   - `GET {MCP_SERVICE_URL}/v1/mcp/servers` (list)
   - `GET {MCP_SERVICE_URL}/v1/mcp/servers/{id}` (get)
   - `PUT {MCP_SERVICE_URL}/v1/mcp/servers/{id}` (update)
   - `DELETE {MCP_SERVICE_URL}/v1/mcp/servers/{id}` (delete)
4. The microservice performs the DB operation and returns the result

### Request Flow: Test Connection / Probe

1. User clicks "Test Connection" on the MCP Registry page
2. Backend forwards to `POST {MCP_SERVICE_URL}/v1/mcp/test-connection`
3. The microservice creates a temporary MCP session (STDIO subprocess or SSE connection), discovers tools, and returns the count
4. For probing a registered server: `POST {MCP_SERVICE_URL}/v1/mcp/servers/{id}/probe` — looks up decrypted config from DB, connects, and returns tool names

### Request Flow: Agent Builder Tool Discovery

1. User selects an MCP server in the Agent Builder's MCPToolsNode component
2. The component calls `list_tools_via_service(server_id, session_context)` from `mcp_service_client.py`
3. This sends `POST {MCP_SERVICE_URL}/v1/mcp/servers/{id}/tools` with optional `session_context`
4. The microservice:
   a. Fetches the server's decrypted config from `mcp_registry` table
   b. Determines mode (STDIO or SSE)
   c. Connects via the appropriate MCP client (reusing existing sessions when possible)
   d. Calls `session.list_tools()` on the MCP protocol session
   e. Returns tool schemas (name, description, raw JSON Schema `inputSchema`)
5. The backend reconstructs `StructuredTool` objects from the returned JSON schemas using `create_input_schema_from_json_schema()` (which stays in the backend)

### Request Flow: Agent Builder Tool Invocation

1. User executes a flow containing an MCPToolsNode
2. `build_output()` is called on the component
3. The component calls `invoke_tool_via_service(server_id, tool_name, arguments, session_context)` from `mcp_service_client.py`
4. This sends `POST {MCP_SERVICE_URL}/v1/mcp/tools/invoke` with the tool request
5. The microservice:
   a. Fetches decrypted config
   b. Connects/reuses session (using `session_context` for affinity)
   c. Calls `client.run_tool(tool_name, arguments)` on the MCP client
   d. Extracts content items (text, image, structured) from the MCP result
   e. Returns `InvokeToolResponse` with content items
6. The backend wraps the response in a `_RemoteToolResult` and returns a `DataFrame`

### How Session Context Works Across HTTP

1. Backend `MCPToolsNode._get_session_context()` computes `f"{graph.session_id}_{server_name}"`
2. This context string is passed in the HTTP request body to the microservice
3. Microservice passes it to `MCPSessionManager.get_session(context_id, ...)` for session reuse
4. Multiple tool calls within the same flow execution share the same MCP subprocess/SSE connection
5. Idle sessions are cleaned up by the microservice's background task

## Microservice API Endpoints

All endpoints except `/health` require the `x-api-key` header.

### Health

| Method | Path | Description |
|--------|------|-------------|
| GET | `/health` | Health check (no auth required) |

### MCP Server Registry CRUD

| Method | Path | Description |
|--------|------|-------------|
| GET | `/v1/mcp/servers` | List registered MCP servers. Query param: `active_only` |
| POST | `/v1/mcp/servers` | Register a new MCP server |
| GET | `/v1/mcp/servers/{id}` | Get a single server by UUID |
| PUT | `/v1/mcp/servers/{id}` | Update a server |
| DELETE | `/v1/mcp/servers/{id}` | Delete a server |

### Test Connection & Probe

| Method | Path | Description |
|--------|------|-------------|
| POST | `/v1/mcp/test-connection` | Test an ad-hoc MCP connection (not from registry) |
| POST | `/v1/mcp/servers/{id}/probe` | Probe a registered server: connect and discover tools |

### Tool Discovery & Invocation

| Method | Path | Description |
|--------|------|-------------|
| POST | `/v1/mcp/servers/{id}/tools` | Discover tools on a server (returns JSON Schemas) |
| POST | `/v1/mcp/tools/invoke` | Invoke a specific tool on a server |

## Supported Transport Modes

| Mode | Transport | Description |
|------|-----------|-------------|
| `stdio` | Subprocess | MCP server runs as a local subprocess (e.g., `npx @modelcontextprotocol/server-filesystem`) |
| `sse` | HTTP SSE | MCP server runs as an HTTP server with Server-Sent Events |

## Encryption Key Derivation

The microservice shares the same `mcp_registry` table with the backend. Secrets (env_vars, headers) stored in this table are encrypted using Fernet symmetric encryption. The encryption key is derived from `WEBUI_SECRET_KEY`:

```
WEBUI_SECRET_KEY  -->  SHA-256 hash  -->  base64url encode  -->  Fernet key
```

Both the backend and microservice must derive the same key from the same `WEBUI_SECRET_KEY` to encrypt/decrypt secrets consistently.

## How Tool Schemas Are Serialized

**Microservice side:** MCP `session.list_tools()` returns tools with `tool.inputSchema` (raw JSON Schema dict). The microservice wraps these as `ToolSchema(name, description, input_schema=tool.inputSchema)` and returns JSON.

**Backend side:** `MCPToolsNode` receives the JSON, calls `create_input_schema_from_json_schema(raw_input_schema)` to build a Pydantic model, then creates `StructuredTool(args_schema=...)`. This function already exists at `base/mcp/util.py` and stays in the backend — it has no MCP SDK dependency.

## Session Management

The MCP microservice manages all MCP sessions (STDIO subprocesses and SSE connections) via `MCPSessionManager`:

- **Session pooling**: Sessions are keyed by server identity (command+args for STDIO, URL+headers for SSE), not by context ID
- **Session reuse**: Multiple tool calls within the same flow execution share the same MCP session via `session_context`
- **Max sessions**: Configurable limit per server (default: 10) to prevent resource exhaustion
- **Idle timeout**: Sessions idle for longer than `session_idle_timeout` (default: 400s) are automatically cleaned up
- **Periodic cleanup**: Background task runs every `session_cleanup_interval` (default: 120s)
- **Health checks**: Before reusing a session, a connectivity test (`list_tools()`) validates it's still alive
- **Graceful shutdown**: On microservice shutdown, all sessions are cancelled and subprocesses terminated

## Running the Microservice

```bash
cd src/services/mcp-service
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -e .
cp .env.example .env           # Configure DB URL, encryption key, API key

```

curl http://localhost:8002/health

## Database

The microservice connects to the **same PostgreSQL database (coredb)** as the main backend. It reads/writes the `mcp_registry` table. No additional database setup or migrations are needed.

The `mcp_registry` table stores:
- Server name (unique), description
- Mode ("sse" or "stdio")
- SSE URL (for SSE mode)
- Command, args (for STDIO mode)
- Encrypted env_vars (Fernet JSON)
- Encrypted headers (Fernet JSON)
- Active/inactive status
- Created by, timestamps
